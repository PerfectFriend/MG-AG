## 2. Игровой движок: Правила «Бешеных Нард» (Crazy Backgammon)

### 2.1. Координатная система доски
* Доска состоит из 24 пунктов (pips), пронумерованных от $1$ до $24$.
* **Белые (WHITE / Игрок 1)**:
  * Движение: по возрастанию номеров от $1$ к $24$.
  * Дом белых: пункты $19$–$24$.
  * Бар для выбитых белых: виртуальный пункт $0$ (вход на $1..6$).
  * Сброс с доски (Bear-off): с пунктов $19..24$ на виртуальный пункт $25$.
* **Чёрные (BLACK / Игрок 2)**:
  * Движение: по убыванию номеров от $24$ к $1$.
  * Дом чёрных: пункты $6$–$1$.
  * Бар для выбитых чёрных: виртуальный пункт $25$ (вход на $24..19$).
  * Сброс с доски (Bear-off): с пунктов $6..1$ на виртуальный пункт $0$.

### 2.2. Начальная расстановка (по 15 фишек)
* **Белые**:
  * 2 фишки на пункте 24 (голова противника)
  * 5 фишек на пункте 13
  * 3 фишки на пункте 8
  * 5 фишек на пункте 6
* **Чёрные**:
  * 2 фишки на пункте 1
  * 5 фишек на пункте 12
  * 3 фишки на пункте 17
  * 5 фишек на пункте 19

### 2.3. Специфические правила «Crazy Backgammon»
1. **Запрет внутренних ходов в доме**:
   * Когда ВСЕ 15 фишек игрока заведены в дом (пункты 19–24 для белых, 1–6 для чёрных), ходы между пунктами внутри дома **категорически запрещены**.
   * Разрешены исключительно ходы на сброс (выброс фишек за пределы доски).
2. **Передача неиспользованных ходов сопернику (Forfeit Transfer)**:
   * Если у текущего игрока нет допустимых ходов для одного или нескольких выпавших кубиков, оставшиеся неиспользованные значения кубиков **передаются противнику**. Противник обязан походить переданными значениями, если имеет легальные ходы.
3. **Каскадный куш (Cascading Doubles)**:
   * При выпадении дубля $X:X$ игрок делает 4 хода по $X$.
   * После этого каскадно активируются 4 хода по $(X+1)$, затем по $(X+2)$ и так далее вплоть до $6:6$.
   * *Пример*: при броске $4:4$ игрок получает четыре хода по 4, затем четыре хода по 5, затем четыре хода по 6 (всего 12 ходов).
4. **Выбивание на бар (Hitting Blots)**:
   * Пункт с ровно 1 фишкой считается открытым (blot). При приземлении фишки соперника фишка выбивается на бар.
   * Игрок, имеющий фишки на баре, обязан вернуть их на доску в первую очередь.

### 2.4. Куб удвоения (Doubling Cube)
* Доступные значения: $2, 4, 8, 16, 32, 64$.
* Игрок в свой ход перед броском костей может предложить удвоить ставку (`DOUBLING_OFFER`).
* Соперник отвечает (`DOUBLING_RESPONSE`):
  * `accept`: ставка удваивается, владение кубом переходит к принявшему.
  * `reject`: соперник признает поражение в текущем гейме со старой ставкой.
* Очки за победу: Обычная = $1 \times \text{cube}$, Марс = $2 \times \text{cube}$, Кокс = $3 \times \text{cube}$.

## 3. Спецификация криптографических костей (Mental Poker ZKP Engine)

Каждый бросок костей рассчитывается децентрализованно без доверенного сервера. Ни один игрок не может повлиять на результат или узнать его заранее.

### 3.1. Алгоритм рукопожатия

```
Игрок A                                                  Игрок B
   │                                                        │
   │ 1. Генерация: r_A (32 байта), v_A ∈ [0..5]            │ 1. Генерация: r_B (32 байта), v_B ∈ [0..5]
   │    C_A = HMAC-SHA256(r_A, byte(v_A))                  │    C_B = HMAC-SHA256(r_B, byte(v_B))
   │                                                        │
   │────── DICE_COMMIT: hex(C_A) ──────────────────────────►│
   │◄───── DICE_COMMIT: hex(C_B) ───────────────────────────│
   │                                                        │
   │ 2. Проверка получения C_B                             │ 2. Проверка получения C_A
   │                                                        │
   │────── DICE_REVEAL: hex(r_A):v_A ──────────────────────►│
   │◄───── DICE_REVEAL: hex(r_B):v_B ───────────────────────│
   │                                                        │
   │ 3. Верификация:                                       │ 3. Верификация:
   │    HMAC(r_B, v_B) == C_B?                              │    HMAC(r_A, v_A) == C_A?
   │                                                        │
   │ 4. Расчет исхода:                                      │ 4. Расчет исхода:
   │    D1 = ((v_A + v_B) mod 6) + 1                        │    D1 = ((v_A + v_B) mod 6) + 1
   │    S = SHA256(r_A || r_B)                              │    S = SHA256(r_A || r_B)
   │    D2 = ((S[0] ⊕ S[1]) mod 6) + 1                      │    D2 = ((S[0] ⊕ S[1]) mod 6) + 1
   ▼                                                        ▼
                    СОВПАДЕНИЕ РЕЗУЛЬТАТОВ (D1, D2)
```

### 3.2. Математические формулы
* Обязательство (Commitment):
  $$C = \text{HMAC-SHA256}(K = \text{seed}[32], \text{Data} = [\text{secretValue}])$$
* Верификация (Reveal Verification):
  Если $\text{HMAC-SHA256}(r_{\text{peer}}, v_{\text{peer}}) \neq C_{\text{peer}}$, выставляется флаг `FRAUD_DETECTED`, бросок аннулируется, противнику присуждается дисквалификация.
* Финальные значения кубиков:
  $$D_1 = ((v_A + v_B) \pmod 6) + 1$$
  $$S = \text{SHA-256}(r_A \parallel r_B)$$
  $$D_2 = ((S[0] \oplus S[1]) \pmod 6) + 1$$

## 4. Спецификация P2P-пакетов (Wire Format & Protocol)

Все сообщения передаются через транспортные каналы (SimpleX SMP, Tor TCP, WebSocket) в виде JSON объекта `GameTurnPacket` либо текстовой строки `$ACTION: $PAYLOAD`.

### 4.1. Схема GameTurnPacket (JSON)

```json
{
  "seq": 104,
  "sender": "Alice",
  "color": "WHITE",
  "action": "MOVE",
  "payload": "24->20",
  "ts": 1729153200000,
  "hmac": "a1b2c3d4..."
}
```

| Поле | Тип | Описание |
|---|---|---|
| `seq` | Long | Монотонно возрастающий номер очереди (защита от replay attack) |
| `sender` | String | Никнейм отправителя |
| `color` | String | `"WHITE"` или `"BLACK"` |
| `action` | String | Код действия (см. таблицу ниже) |
| `payload` | String | Содержимое действия |
| `ts` | Long | UNIX таймштамп в миллисекундах |
| `hmac` | String | Опциональная HMAC-подпись пакета |

### 4.2. Допустимые команды Action и формат Payload

| Action | Payload Формат | Пример | Описание |
|---|---|---|---|
| `DICE_COMMIT` | `<hex64_commitment>` | `DICE_COMMIT: e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` | Передача SHA-256 хэша сида |
| `DICE_REVEAL` | `<hex64_seed>:<int_0_5>` | `DICE_REVEAL: 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08:4` | Открытие сида и значения |
| `MOVE` | `<from>-><to>` | `MOVE: 24->20` (или `MOVE: 0->20` с бара) | Перемещение шашки |
| `BEAR_OFF` | `<from>-><target>` | `BEAR_OFF: 24->25` (белые) или `BEAR_OFF: 1->0` (черные) | Выброс шашки за доску |
| `PASS` | `"none"` | `PASS: none` | Пропуск хода при отсутствии доступных ходов |
| `DOUBLING_OFFER` | `<multiplier_int>` | `DOUBLING_OFFER: 2` | Предложение удвоить ставку |
| `DOUBLING_RESPONSE`| `"accept"` или `"reject"` | `DOUBLING_RESPONSE: accept` | Ответ на предложение удвоения |
| `CHAT` | `<utf8_string>` | `CHAT: Отличный ход!` | Текстовое сообщение в чате |
| `VOICE` | `<durationSec>:<transcript>:<base64>`| `VOICE: 3:Привет!:GkXfo59...` | Голосовой пакет рации Walkie-Talkie |

## 5. Спецификация E2E-шифрования (Double Ratchet Vault)

Для сквозного шифрования между игроками используется протокол Double Ratchet (совместимый со спецификацией Signal / SimpleX).

### 5.1. Криптографические примитивы
* **KDF Root Key**: RFC 5869 HKDF-SHA256.
* **Diffie-Hellman Ratchet**: Эллиптическая кривая `secp256r1` (NIST P-256).
* **AEAD Cipher**: AES-256-GCM.
* **Header AAD**: `"$senderDhPublicKeyHex|$sequenceNumber|$previousChainLength"`.
* **Traffic Padding**: Фиксированный размер каждого зашифрованного пакета — ровно **16384 байта (16 КБ)**. Формат открытого блока:
  `[4 байта: длина полезной нагрузки N] + [N байт полезной нагрузки] + [(16380 - N) байт случайного шума SecureRandom]`.
* **Out-of-Order Key Store**: Хранилище до $MAX\_SKIP = 256$ пропущенных ключей для дешифровки пакетов при нарушении порядка доставки в сети.

## 6. Сетевой транспорт и Discovery

### 6.1. Локальный поиск (Zero-Config LAN UDP Broadcast)
* **Порт**: UDP `8888`.
* **Адрес отправки**: `255.255.255.255`.
* **Формат широковещательного пакета**:
  ```
  MADGAMMON_ROOM:<HostPlayerName>:<HostEndpointIP:Port>
  ```
  *Пример*: `MADGAMMON_ROOM:Alex:192.168.1.45:8080`
* **Интервал маяка (Beacon)**: 2000 мс. При получении пакета клиент автоматически отображает комнату в списке доступных матчей.

### 6.2. SimpleX SMP (Simple Messaging Protocol)
* Соединение по WebSocket WSS: `wss://smp.simplex.im` (или через локальный SOCKS5 `127.0.0.1:10808` / `9050`).
* Создание очередей:
  * Send Queue (A $\to$ B)
  * Receive Queue (B $\to$ A)
* Ссылка-приглашение (Contact URI):
  `simplex://contact?v=2-4&smp=smp%3A%2F%2Fsmp.simplex.im%2F<queue_id>`

### 6.3. Нативный сокетный транспорт (Tor Onion / Direct TCP)
* Порт хоста по умолчанию: TCP `8080`.
* При наличии скрытого сервиса Tor используется v3 `.onion` адрес вида `<56_chars>.onion:8080`.
* При прямом LAN-подключении используется IP-адрес хоста в подсети.

## 7. Блокчейн-биллинг и RPC-верификация

### 7.1. Схемы платежных ссылок (BIP-21)
* **Monero (XMR)**: `monero:<address>?tx_amount=<amount>&tx_description=<invoiceId>`
* **USDT TRC-20**: `tron:<address>?amount=<amount>`
* **Bitcoin (LN/On-Chain)**: `bitcoin:<address>?amount=<amount>&label=<invoiceId>`

### 7.2. Публичные RPC эксплореры для верификации ончейн
* **Bitcoin**: `https://mempool.space/api/tx/{txid}` — ожидается `status.confirmed == true`.
* **USDT TRC-20**: `https://apilist.tronscanapi.com/api/transaction-info?hash={txid}` — ожидается `contractRet == "SUCCESS"`.
* **Monero**: `https://api.blockchair.com/monero/raw/transaction/{txid}` — проверка наличия в блокчейне.

## 8. Аудио-рация (Walkie-Talkie) и стриминг
* **Формат записи**: 3GP / AAC-LC, моно, 16 000 Гц, битрейт 32 кбит/с.
* Пакет кодируется в Base64 и передается действием `VOICE`.
* На стороне получателя файл пишется во временный кэш и воспроизводится через стандартный аудиотракт.
